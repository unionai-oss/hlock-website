The package manager for agent harnesses

Your agent harness
made portable.

Your agent is more than a model. It's a harness, MCP servers, skills, and config, hand-tuned on one machine. hlock is the missing harness packaging layer: harness.lock tracks all of its dependencies, so you can commit it to git and restore it anywhere.

Works with Claude Code, Codex, Pi, OpenCode, Cursor, Gemini CLI and more.

The fix

          
One file.
Every dependency.

          

            hlock pin reads the harness you already use and writes everything it depends on
            into harness.lock: versions, sources, digests. Hand-written skills and config
            are vendored next to it in .hlock/, so the pair is self-contained.
          

          
    
            
  • Harness version and install source
    • 
            
  • Models per role, and where each came from
    • 
            
  • MCP servers, normalized across config formats
    • 
            
  • Skills, plugins & instructions, each with a digest
    • 
            
  • Secrets as placeholders, never values
    •

Safe to commit

          
Secrets stay out.
Always.

          

            pin never writes a secret. API keys, tokens, auth headers, and
            credential-looking values become HLOCK_SECRET_* placeholders.
            You supply the values when you sync, and a real secret is never replaced with a placeholder.
          

        

        

          

            
~/.claude.json


"github": {
  "command": "npx",
  "env": {
    "GITHUB_TOKEN": "ghp_8kQx2LmZ0vYt…""${HLOCK_SECRET_GITHUB_GITHUB_TOKEN}"
  }
}

          

          

            
              
            
            1 secret redacted · supplied as HLOCK_SECRET_* when syncing
          

        

      

    


    
    

      

        
Rehydrate anywhere

        
Same agent. Any machine.

        
hlock sync builds a plan: what's already satisfied, what it does for you, and the exact command for anything it can't.

        

          

            

              
            

            
A new laptop

            
Clone the repo, sync, set your secrets. Your config, skills, and plugins land where the harness expects them.

            
$ git clone …/my-app && cd my-app
$ hlock sync --install

          

          

            

              
            

            
An isolated env

            
Like a virtualenv for your harness. Materialize the lock into its own config root and leave yours untouched.

            
$ hlock sync --prefix .hlock/env
✓ in sync at .hlock/env/claude-code/config

          

          

            

              
            

            
A container

            
Write a Docker build context with the restored config baked into the image's home. Ship your agent to CI or a cluster.

            
$ hlock sync --docker
✓ wrote .hlock/docker/pi/Dockerfile

          

        

        

          tip
          
Some steps need a human, like installing an app or setting a secret. hlock sync --skill writes an Agent Skill from the plan, so any agent can finish the job for you.

Lock without lock-in

          
Feeling FOMO on
yet another new harness?

          

            Every week there's a fresh harness — or a proprietary model gated behind one — and it
            starts to out-shine yours. But your setup won't move. hlock migrate moves
            the whole thing in one command: skills, MCP servers, and prompts rewritten to where the
            new harness reads them, models mapped to a provider it supports.
          

          
    
            
  • Try it tonight — a migrated lock runs in isolation before you commit
    • 
            
  • Skills & instructions move to the directories it reads (CLAUDE.md → AGENTS.md)
    • 
            
  • Models remapped to a provider the new harness supports
    • 
            
  • Source lock untouched — no risk switching back
    • 
          

          

            Any lock works as the source — pinned, resolved, tuned, or pulled. hlock localize
            is just a migration that also goes local. Because the lock is a committed file, review what
            moves with hlock diff before you switch.
          

          Read the hlock migrate guide

The meta harness

          
Let an agent do
the busywork.

          

            Some jobs need judgment, not a script. hlock meta hands them to an agent, the
            meta harness, so you don't have to do them by hand.
          

          
    
            
  • installInstalls what the sync plan leaves to you, then runs hlock sync --yes.
    • 
            
  • bootstrap-evalsFills your eval packs with real tasks from your repo.
    • 
            
  • updateMoves skills, MCP servers, and plugins to their latest releases. --pin records it in the lock.
    • 
          

          

            Use the built-in agent or a harness you already have (Pi, Codex, Goose, OpenCode, Hermes), with
            --local for open-weight models. It asks before every command, or runs --headless against an allowlist.

Trust & containment

          
It's a lock, but is it
safe to run?

          

            A lock you pull from someone else is a program you're about to run. hlock
            checks what a lock would place before you run it, then runs the agent where it can't
            touch the rest of your machine.
          

          
    
            
  • auditScans for hidden characters and executables, enforces your hlock-policy.toml, and writes an SBOM.
    • 
            
  • sandboxRuns the agent through Docker or OpenShell with no capabilities — your home dir and Docker socket are never mounted.
    • 
            
  • check --lockedFails the build if harness.toml and harness.lock drift, like uv sync --locked. audit --ci emits SARIF for code scanning.
    • 
          

          

            The sandbox is recorded in the lock, so a teammate who pulls it gets the same one.
            In a shared repo, each contributor keeps their own harness.<handle>.lock, and
            hlock diff shows the text behind any digest that changed.
          

          Read the audit & sandbox guides
        

      

    


    
    

      

        
Then make it better

        
A locked harness is a baseline.

        
Once your setup is reproducible, you can measure it. Every lock hlock resolves records its success rate, cost, and latency on your own tasks.


        

          

            

              hlock resolve
              like uv lock
            

            
Find the best stack for your tasks

            
Draft an eval pack from the sessions your agent already logged, list the models and harnesses to try in harness.toml, and lock the winner with its evidence.

            

              
            

            Read the hlock resolve guide
          


          

            

              hlock tune
              like PGO
            

            
Tune what's inside

            
Go past model choice into prompts, hyperparameters, and fine-tuned small models, on your evals. Run locally, on a devbox, or lift trials to a Flyte cluster for GPUs.


$ hlock tune --backend cluster --depth ft

            Read the hlock tune guide
          


          

            

              hlock upgrade
              like uv --upgrade
            

            
Stay current, automatically

            
New models and components come out all the time. hlock upgrade tells you which locked pieces have newer versions, re-measures the stack on your evals, and keeps the previous lock so you can roll back. If the success rate drops, it rolls back on its own.


$ hlock upgrade --all --apply
✓ planner qwen-7b → qwen-32b

            Read the hlock upgrade guide

quickstart


$ pip install hlock
$ hlock pin                      # lock your current setup into harness.lock
$ git add harness.lock .hlock/   # version it (secrets are placeholders)
$ hlock check                    # see what changed since the pin
$ hlock sync                     # on another machine: rehydrate it
$ hlock launch                   # start a session on the locked setup
